# CyberSWE task history: what actually made tasks hard or easy

This is a retrospective on task packages and downloaded agent traces, not a ranking based on advisory prose. A score is meaningful only for the exact task version, model, and verifier used for that run. In particular, a green graded run is not automatically a *true* security fix, and a zero is not necessarily evidence that the model reasoned incorrectly about the intended bug. For these cases the intended calibration bar was **1–5 genuine passes out of eight GPT-6.1 Sol rollouts**; weaker-model runs are useful for fairness checks, not a substitute denominator.

| Case | Observed result | Main selection lesson |
| --- | --- | --- |
| cargo-nextest | 8/8 graded Sol passes | The existing typed parser made the apparent multi-format problem nearly one decision. |
| Hickory DNSSEC | First version: 8/8 graded, with false passes; later: 1/8 graded | The benign multi-key fallback exposed an incomplete fix; this candidate is not inherently bad. |
| Quinn | Latest version: 5/8 graded | A count-of-chunks test and a broad symptom make the apparent difficulty uncertain. |
| rkyv | Seven downloaded Sol failures, not eight; one Luna pass, on an older version | Models mostly repaired another real archive bug; low scores did not measure the intended repair. |
| tendermint-rs | Final version: 2/8 graded Sol passes | One identity invariant crossed decoding and vote counting, and concrete bypasses separated partial from full repairs. |
| Cosmos EVM GHSA-54gx | Current version: 2/8 graded Sol passes; promising but unresolved | One nested-state consistency failure had two observable consequences, but an open gameability finding still needs resolution. |
| Cosmos EVM GHSA-mjfq | 4/8 graded Sol passes | Snapshot-and-rollback semantics spanned state, events, gas errors, and call wrappers; alternative correct designs could pass. |

## Four candidates whose original predictions did not hold up cleanly

### cargo-nextest — [GHSA-vc25-qg58-w57c](https://github.com/nextest-rs/nextest/security/advisories/GHSA-vc25-qg58-w57c)

Evidence: [task ZIP](/home/zoomer/Desktop/micro1/nextest-ghsa-vc25-qg58-w57c/nextest-ghsa-vc25-qg58-w57c.zip); eight GPT-6.1 Sol runs `176340e6`, `47891926`, `6dd42efa`, `a901c9f5`, `a97e6ba4`, `adfb2138`, `d70d42f9`, `e94bfa93`. All scored 2/2 F2P and 122/122 P2P.

The premise sounded like a difficult trust-boundary trace: imported portable recordings supplied build-scope strings later forwarded to Cargo, where an option-looking string could become configuration. In the actual repository, however, `CargoBuildScopeOptions` and its Clap parsing already supplied the relevant structure. Every Sol patch converged on checking/parsing the recorded options before the single forwarding loop in `cargo-nextest/src/dispatch/core/base.rs`. The visible F2P cases chiefly exercised split and combined `--config`; they did not establish the proposed matrix of legacy formats, option-looking *values*, and all replay paths. One patch (`6dd42efa`) rejected recorded option **values** beginning with `-`, which might reject legitimate use; the graded P2P set did not settle that compatibility question.

**Assessment:** genuinely too easy at the tested boundary, with an additional verifier-breadth caveat. The large repository and scary “attacker-controlled Cargo arguments” description masked a short path to an existing typed abstraction. Do not count the eight greens as proof that every plausible variant or benign recording was preserved. A better pre-prototype question would have been: *After opening the replay code, how many independent security decisions remain?* Here the answer was essentially one.

### Hickory DNSSEC — [GHSA-37wc-h8xc-5hc4](https://github.com/hickory-dns/hickory-dns/security/advisories/GHSA-37wc-h8xc-5hc4)

Evidence: [task ZIP](/home/zoomer/Desktop/micro1/hickory-dns-ghsa-37wc-h8xc-5hc4/hickory-dns-ghsa-37wc-h8xc-5hc4.zip). The original two-F2P version graded 8/8 Sol passes, but patches `05a5b3ac`, `299d2248`, `3e644f00`, `889113a3`, and `f3a699df` returned early when *any* DNSKEY in the set matched an anchor. That can skip a different, legitimately DS-authenticated signer. The later five-F2P, 116-P2P version graded 1/8: `cee6cfb6` passed; `03da28e0`, `31910cf1`, `42eadf90`, `b82e8bb3`, and `dbb42eb4` passed all F2P but failed `accepts_ds_covered_signer_beside_trust_anchor`; `60527ffe` and `d1059935` worked on signature validity rather than the trust transfer and failed F2P.

The core bug is a real identity mistake: proof that one key is trusted must not automatically authorize another key merely because both appear in the same RRset. The first tests checked rejection of the attacker key, but not preservation of the legitimate alternate signer in a mixed RRset. The added P2P case exposed a characteristic “secure but broken” repair: bind verification to the anchor and accidentally remove a valid DS path. This is exactly the kind of benign counterpart a security regression needs.

**Assessment:** do not label this candidate intrinsically bad or too easy. The *initial verifier* was too weak, and its 8/8 rate was misleading; the later version shows a credible partial-fix split. It is not submission-ready on the inspected evidence because the packaged `reasoning.txt` still contains the literal draft placeholder, although older QC artifacts describe completed reasoning; those reports are stale for this package. The mixed anchor/DS contract also deserves explicit protocol review. Selection lesson: for authentication code, ask what legitimate *other* identity must still work, not just which attacker identity must fail.

### Quinn — [GHSA-qfwj-vfxf-92j2](https://github.com/quinn-rs/quinn/security/advisories/GHSA-qfwj-vfxf-92j2)

Evidence: [task ZIP](/home/zoomer/Desktop/micro1/quinn-ghsa-qfwj-vfxf-92j2/quinn-ghsa-qfwj-vfxf-92j2.zip). An earlier eight-run set graded 4/8; the latest graded 5/8 (passes `9270bc61`, `60455456`, `e790ccb1`, `597daf2f`, `c94dde58`). `7e55efb0` fixed the unordered-overlap route but missed the many-small-gaps case. `36bbf99f` and `f9c46aa2` worked on datagram receive memory, a different problem, and failed both F2P cases.

The advisory describes small gapped frames bypassing an earlier defragmentation guard because its `over_allocation` condition is peer-controllable. The unordered-overlap path is an additional case in the authored task, not something established by the advisory. F2P constructs encrypted packets and feeds the real `quinn-proto` endpoint/connection, but its resource assertion drains the unordered reader and accepts either connection closure or fewer than 8,192 **returned** chunks. This is an indirect proxy for retained memory, not a direct measurement or demonstrated upper bound. A compact representation could return many chunks safely, while fewer large or expensive allocations might still consume too much memory. The advisory's larger, multi-stream resource pattern is not reproduced. The verifier grades `quinn-proto` library tests, not the separate high-level `quinn` crate even though some agents edited it. The broad symptom also sent two agents toward datagram buffering.

**Assessment:** a numerical 5/8 at the threshold does not by itself prove this was a sound task. The interesting branch distinction is real, but resource tests should measure retained memory or establish a rigorous bound from their count proxy across sizes, overlaps, and streams, while P2P preserves legal reordering near the limit. Also distinguish a model that chose the wrong resource subsystem from one that understood stream reassembly but made an incomplete repair. This is a promising hypothesis with a measurement/localization problem, not a proven unsalvageable vulnerability.

### rkyv — [RUSTSEC-2026-0235](https://rustsec.org/advisories/RUSTSEC-2026-0235)

Evidence: [task ZIP](/home/zoomer/Desktop/micro1/rkyv-rustsec-2026-0235/rkyv-rustsec-2026-0235.zip). The downloaded artifacts contain **seven**, not eight, GPT-6.1 Sol runs (`6eaa0f94`, `6ec5b61d`, `d16c1e96`, `d6a51fa7`, `d981afe4`, `f143fb73`, `fa273ed3`), each 0/6 F2P and 106/106 P2P. The eighth downloaded run, `66672bc7`, is **GPT-6 Luna** and scored 6/6 plus 106/106. These runs used an older six-F2P/106-P2P version; the inspected package now has seven F2P and 109 P2P. No current-version eight-Sol conclusion is available.

The intended flaw is subtle: shared-pointer validation remembered an address and type but omitted unsized metadata such as slice length, allowing a second view of the same bytes to reuse a shorter validation. Yet every downloaded Sol patch changed `swiss_table/{table,index_map}.rs`, targeting a different plausible malformed-archive memory-safety issue rather than the shared-pointer validation path. The base repo offered at least two independently repairable bugs matching the prompt's “malformed archives that reuse values” and “invalid memory reads.” The zero scores therefore mostly measured *which bug the agent localized*, not whether it could reason about pointer metadata. The Luna passing patch introduced a metadata-aware `SharedContext` method with a default that delegates to the old metadata-ignorant method; a public custom-context route may remain, but that bypass has not been demonstrated, so its green score is not independently verified as complete.

**Assessment:** the candidate is not proven too hard. The observed experiment was confounded by ambiguous localization, an incomplete run set, and version drift. A better symptom would distinguish two safe views of the *same shared object* with different extents without spelling out the missing metadata field. Then rerun eight Sol rollouts on that exact version and test any public customization hooks. Do not treat “0/7 Sol” plus “1/1 Luna” as the required difficulty result.

## Three instructive task designs—not all ready for submission

### tendermint-rs — [GHSA-6jrf-4jv4-r9mw](https://github.com/cometbft/tendermint-rs/security/advisories/GHSA-6jrf-4jv4-r9mw)

Evidence: [task ZIP](/home/zoomer/Desktop/micro1/tendermint-rs_isa-2025-003/tendermint-rs_isa-2025-003.zip) and [trace review](/home/zoomer/Desktop/micro1/tracereviews/tendermint-rs-isa-2025-003). On the final nine-F2P/106-P2P version, Sol runs `250516cf` and `1286d9da` passed. Five runs (`f8e2fa2c`, `b650414f`, `297eb8f0`, `ae49f728`, `8f7e00ce`) reached 7/9 F2P: they tied signature-cache results to a public key but still let one signing key appear under distinct addresses. `bd108cfc` reached 6/9 by rejecting duplicate addresses only, missing unique-address cross-set reuse.

The prompt exposed the observable failure—successful light-client verification without support from enough *independent* validators—without naming files or the repair. The root property is compact: a signature from one signing identity must not be counted as independent voting power twice. The real fix spans validator address/public-key consistency at decoding and vote accounting at runtime; those are two representations of the **same identity invariant**, not two arbitrarily bundled vulnerabilities. The tests used real signatures and the public production verifier offline, with fixed time, a genuine-majority accept case, insufficient-majority reject case, and variations of address, key, and weight. They asserted the verdict, not the gold patch's exact function calls, so alternative key-aware and deduplicating repairs could pass.

The first version had fewer F2P tests and allowed partial repairs to score green. Inspecting those green patches produced concrete bypass cases, which were added before the final calibration. This is the valuable pattern: **a plausible repair can be correct at one representation boundary but wrong at another**, and the test suite demonstrates the bypass rather than merely asserting implementation details. Caveat: the multi-location invariant has to remain a connected exploit chain; adding unrelated validator hardening solely to make the task harder would spoil that property.

### Cosmos EVM ICS20 balance reuse — [GHSA-54gx-3cgr-7mfm](https://github.com/cosmos/evm/security/advisories/GHSA-54gx-3cgr-7mfm)

Evidence: [task ZIP](/home/zoomer/Desktop/micro1/cosmos-evm-ghsa-54gx-3cgr-7mfm/cosmos-evm-ghsa-54gx-3cgr-7mfm.zip), [trace review](/home/zoomer/Desktop/micro1/tracereviews/cosmos-evm-54gx.txt), and [current gameability probe](/home/zoomer/Desktop/micro1/cosmos-evm-ghsa-54gx-3cgr-7mfm/qc_artifacts/probes/gameability.md). On the current four-F2P/493-P2P version, `4bd1b3f0` and `cab04f53` passed; six Sol patches (`61ebcb49`, `8e5a08cf`, `b2ea49c7`, `b9798d12`, `bb53c220`, `dcfc76cb`) reached 3/4 F2P and 493/493 P2P. They repaired the stale ERC20 storage leg but missed the native-balance case after a nested precompile revert.

Here one nested execution flow crosses the outer EVM StateDB, Cosmos cached state, event manager, and ICS20 precompile. The outer state can flush stale ERC20 storage after a nested write; a nested rollback can also replace the active cache/event context while a caller continues with an earlier reference and loses a native-balance debit. Either consequence can leave a sender's apparent balance too high. The package's evolution matters more than its current score: an earlier storage-only verifier graded five or six Sol patches as passing, but review found those patches still admitted an end-to-end native-balance failure. Adding a real-transaction F2P for that second consequence converted the green-but-incomplete patches into failures. The expanded P2P set covers successful transfers and substantial EVM, precompile, and keeper behavior, helping prevent a “disable the feature” solution. The two current green patches use alternative cache/journal designs, not just the gold layout. The six current failures have the **same** missing native-balance test: the measured difficulty is concentrated at this second-leg cliff rather than six distinct mistakes.

**Important open issue:** this is promising, not conclusively clean. The current gameability probe removes restoration of the processed-event cursor from the gold's rollback journal and still gets 4/4 F2P and 493/493 P2P. That proves the tests do not inspect this internal divergence; the probe proposes a later missed debit but has not demonstrated the full public exploit transaction. Before calling the verifier fair, either reproduce that sink-level bypass and add a targeted test, or show why the divergent cursor cannot cause an observable security failure. Also explicitly justify why the storage and event effects are one connected nested-state problem rather than independent bugs packaged together.

### Cosmos EVM stateful precompile rollback — [GHSA-mjfq-3qr2-6g84](https://github.com/cosmos/evm/security/advisories/GHSA-mjfq-3qr2-6g84)

Evidence: [task ZIP](/home/zoomer/Desktop/micro1/cosmos-ghsa-mjfq-3qr2-6g84/cosmos-ghsa-mjfq-3qr2-6g84.zip) and [trace review](/home/zoomer/Desktop/micro1/tracereviews/cosmos-evm-mjfq.txt). Four Sol runs (`16711d66`, `73faac05`, `85ee1979`, `d055e315`) passed five F2P and 105 P2P with different isolation/rollback implementations. `a7a6b271` passed only one F2P after focusing on ERC20 `transferFrom`; `4bbc078a`, `ba455b26`, and `cb4ca306` protected call setup or early rejection but not state written by an executed precompile.

The security rule is observable and general: a failing inner stateful precompile call must not leave Cosmos state or events behind when its caller continues. The prompt eventually said “failing calls,” not “failed transactions”: an outer transaction may catch an inner failure and succeed, so the latter wording pointed to the wrong contract. The fix has to account for normal errors, out-of-gas, and wrappers that write to multiple state backends. The gold addresses nine concrete precompile `Run` wrappers plus common precompile and StateDB code. F2P exercises real EVM calls and then commits after ignoring the failed result; it checks rewards, delegation, ERC20 allowance, and prior SDK events. P2P preserves ordinary successful behavior. Successful agents were allowed to use child caches or other isolation strategies rather than mirroring the gold patch's exact snapshot calls.

The authoring history supplied a crucial fairness correction. An earlier `TestCMS` regression asserted a particular cache-write mechanism and marked alternative, observably correct designs wrong; removing it in favor of state/event/gas outcomes made the verifier less overspecified. This is a good difficulty source—transactional semantics across layers—not a large diff for its own sake. **Coverage caveat:** the five F2P cases exercise three of the nine concrete wrappers; an older alternative-solution probe reportedly passed a fix limited to those tested wrappers. The other six may permit a partial repair to pass, although a current-version public-sink bypass has not been demonstrated here. The tests also model a caught inner call plus commit rather than every deployed-contract call graph. A green run still merits patch review.

### Short comparator: gnark Grumpkin scalar binding

The Grumpkin soundness flaw was real, but once agents found the relevant GLV arithmetic, binding the decomposition to the supplied scalar was a direct local correction. Weaker models regularly completed it. Making the prompt more obscure mostly changed *whether they found the location*, not the depth of the repair. That is a warning against mistaking cryptographic vocabulary or a long advisory for sustained problem-solving difficulty.

## Selection rules worth reusing

1. **Separate localization difficulty from repair difficulty.** rkyv's zeros and Quinn's datagram detours show that a vague symptom can produce failures unrelated to the intended mechanism. A good prompt identifies a distinctive observable failure while leaving the root cause and fix undisclosed.
2. **Count independent decisions, not changed files.** Nextest had a large repository but a single existing parser and forwarding loop; Cosmos state rollback required maintaining one transaction invariant through several layers. Conversely, a multi-file gold patch can still be reducible to one standard edit.
3. **Prototype the tempting wrong fix before betting on the task.** For each expected partial repair, build the bypass and check that it fails at the real sink. Tendermint's extra signing-identity cases and Cosmos54's native-balance case materially changed the verdicts. If all plausible repairs pass immediately, the candidate may simply be easy.
4. **Pair each security rejection with a benign acceptance case.** Hickory's DS-covered signer beside an anchor caught a repair that stopped the attack by breaking legitimate verification. Preserve compatible recordings, legal fragment reordering, valid shared aliases, and successful transactions for the same reason.
5. **Measure the security property itself.** For resource use, measure retained allocation or prove that the chosen count proxy bounds it; for state bugs, assert final balances/events after a public call, not the presence of a particular journal method or cache write. Avoid tests whose success depends on a specific patch architecture.
6. **Audit green runs and probes as aggressively as red ones.** Green storage-only Cosmos54 patches were false positives. A gameability probe can expose a current gap even when oracle and rollout counts look right; conversely, a probe's hypothetical bypass needs an actual reachable sink before being treated as a confirmed vulnerability.
7. **Keep version and model denominators exact.** Seven Sol runs plus one Luna run are not eight Sol runs, and results from an earlier six-test rkyv package do not validate the current seven-test package. Regrade or rerun after materially changing F2P, P2P, gold, or prompt; do not blend old and new scores.
8. **Price the evidence before committing to a candidate.** The Cosmos54 package is roughly 41 MB with an 84 KB hidden-test patch and 493 graded P2P IDs; it took reviewer-driven redesign and still has an open probe. The Cosmosmj package is roughly 18 MB with a 16 KB hidden-test patch and a comparable pass band, though its wrapper coverage is less certain. A difficult task that needs large integration scaffolding can be valid, but it is expensive to validate and revise; prefer a smaller public-sink reproduction when it proves the same invariant.
